# Unreal Engine on Lynx, 2026-10-22

A probe record, not a ruling. `docs/DECISIONS.md` 2026-10-20 ("never claim UE results from Lynx") is still in force and
outranks this note: nothing here is a reported build result, a suite grade or a baseline. It records what the App Master
measured on Lynx (Windows 11 ARM64) this wake, with its gaps, so the KPI loop stops counting on a premise the measurement
contradicts. Everything in sections 1-7 was measured by the App Master; the builder that wrote this note ran no UE build
and no automation suite. Section 8 is the builder's own measurement (dotnet resolution only, no build).

**Headline:** a complete UE 5.8.4 is installed on Lynx and builds the real editor target cold in 193.75 s, under x64
emulation. The in-engine suite runs here but shows **two off-baseline failures of unknown cause**, so nothing hash-shaped
or conformance-shaped from Lynx can be trusted yet. K4's "cards needing a UE host = Wolf" premise is wrong for editor
builds and right for APKs.

## 8. T51 answered from this machine

T51 asked whether UE 5.8 UBT can use an arm64-hosted compiler. Settled here, so it no longer needs Wolf:

- UBT selects its MSVC host directory from **its own process architecture**. UBT runs as an x64 process (section 3), so
  it picks the x64 host. `...\bin\Hostarm64\x64\cl.exe` is installed and unused.
- `Engine/Binaries/DotNET/UnrealBuildTool/runtimes/` contains `browser-wasm`, `linux-*`, `win`, `win-arm`, `win-x64` and
  `win-x86`, and **no `win-arm64`**. That is the `blake3_dotnet` native chain, so UBT cannot simply be run as an arm64
  process either.
- Net: native-speed compiles on Lynx are not available from the shipped engine; the 193.75 s above is the emulated
  number. The card's status is the App Master's to change; see the "Probe result" section of
  `apps/vr/tasks/T51-ue-arm64-host-probe.md`.

### The dotnet-arch defect in `build.ps1` (builder-measured, no build run)

`Engine/Build/BatchFiles/GetDotnetPath.bat` sets `UE_DOTNET_ARCH=win-arm64` when `PROCESSOR_ARCHITECTURE` is `ARM64`
(or `AMD64` with `ProgramFiles(Arm)` defined), but `Engine/Binaries/ThirdParty/DotNet/10.0/` holds **only `win-x64`**.
`DOTNET_ROOT` then names a directory that does not exist, and `dotnet` falls through PATH to the system host, which
cannot find the framework.

Red, reproduced by the builder in one `cmd` process with `set PROCESSOR_ARCHITECTURE=ARM64` (what a native ARM64 shell
has), then `Build.bat NoSuchTarget Win64 Development` (a bogus target, so nothing could build even if UBT started):

```
Using bundled DotNet SDK version: 10.0 win-arm64
UE_DOTNET_DIR=C:\Program Files\Epic Games\UE_5.8\Engine\Build\BatchFiles\..\..\Binaries\ThirdParty\DotNet\10.0\win-arm64
dotnet.exe ABSENT
Using bundled DotNet SDK version: 10.0 win-arm64
Running UnrealBuildTool: dotnet "..\..\Engine\Binaries\DotNET\UnrealBuildTool\UnrealBuildTool.dll" NoSuchTarget Win64 Development
BUILD_BAT_EXIT=-2147450730
```

`-2147450730` is `0x80008096` (hostfxr FrameworkMissingFailure); its low byte is the 150 the App Master saw. Only
`Build.bat`'s own echo lines print; UBT prints nothing. The old `build.ps1` checked only that `Build.bat` exists and that
`$LASTEXITCODE` is non-null, so it passed that code up with no diagnosis.

Shell nuance: a Git Bash session on Lynx runs x64, so its children see `PROCESSOR_ARCHITECTURE=AMD64` and lose
`ProgramFiles(Arm)` (a name bash cannot hold). From there the engine resolves `win-x64` and the defect does not show.
It shows from a native ARM64 PowerShell or Terminal, which is how the App Master hit it.

Fix (commit 522a306): `build.ps1` mirrors the resolver before calling `Build.bat`. If the engine's arch directory is
missing and `win-x64` is present, it pre-sets `UE_DOTNET_VERSION` (read from `GetDotnetPath.bat`), `DOTNET_ROOT`,
`DOTNET_MULTILEVEL_LOOKUP=0`, `DOTNET_ROLL_FORWARD=LatestMajor` and prepends the directory to PATH, which takes the
resolver's own "UE_DOTNET_VERSION already set" early exit. That is the workaround that produced the 193.75 s build.
With no usable dotnet it exits 4 on stderr, naming the directory. `-ResolveOnly` prints the resolution and never calls
`Build.bat`. Green, `powershell -NoProfile -ExecutionPolicy Bypass -File apps/vr/tools/build.ps1 -ResolveOnly`:

| case | output | exit |
|---|---|---|
| Git Bash (x64) shell as-is | `dotnet: engine default '...\DotNet\10.0\win-x64'` | 0 |
| `PROCESSOR_ARCHITECTURE=ARM64` | `dotnet: win-x64 fallback '...\DotNet\10.0\win-x64' (engine wanted '...\DotNet\10.0\win-arm64', which is missing; UBT runs emulated)` | 0 |
| `AMD64` + `ProgramFiles(Arm)` set | same fallback line | 0 |
| fake `UE_ROOT` with no DotNet | `the engine resolves dotnet to '...\win-arm64', which holds no dotnet.exe, and there is no win-x64 fallback at '...\win-x64'.` + `NOTHING WAS BUILT.` | 4 |
| `UE_DOTNET_VERSION=10.0`, bogus `DOTNET_ROOT` | `UE_DOTNET_VERSION=10.0 is preset but DOTNET_ROOT 'C:\nope' holds no dotnet.exe.` + `NOTHING WAS BUILT.` | 4 |
| `UE_ROOT=C:\nope` | the existing engine-missing message | 2 |

Not proven by the builder: that the patched script, run for real, builds. That rests on the App Master's 193.75 s run
with the same environment, which the builder did not reproduce.

Also observed: the documented `powershell -NoProfile -File apps/vr/tools/build.ps1` is refused on Lynx by the default
